# PicoMarQ 1.3.4 — validation and release status

**Change since 1.3.3** (`history/changes-since-1.3.3.patch`): a newer engine, and nothing else in the program.

- **Electron 44.11.5 in place of 44.6.0.** PicoMarQ runs on Electron, which carries a copy of the Chromium browser engine and of Node.js. The new release has Chromium 152.0.7977.169 (was 152.0.7977.130) and Node.js 24.22.3 (was 24.21.0). It is the same generation of Chromium with the security and bug fixes of the seventeen Electron releases since, so the page engine that the spelling features lean on is the one they were built for. Of the release notes in between, those of 44.7.0, 44.8.0, 44.9.0, 44.10.0, 44.11.0 and 44.11.5 were read: fixes, and nothing that changes a function PicoMarQ uses. Some of the fixes are to the request filter that 1.3.3's barrier against pictures on other computers is built on (two crashes, and requests made by web workers now pass through it too; PicoMarQ starts no web workers).
- **The program is that of 1.3.3.** The compiled program in `dist/` and the main-process files in `desktop/` are byte for byte the same. In `package.json` and `package-lock.json` only the version and the entry for Electron change; no other part was moved (the lock file differs from 1.3.3's in those two entries only).
- **The packaging script** (`scripts/package-windows.cjs`) now compares the checksum of Electron's Windows package with the published one itself, can use a copy fetched beforehand (`PICOMARQ_ELECTRON_ZIP`), and writes `RELEASE-VALIDATION.txt`. It is used again because the engine is new: every release from 1.2.4 to 1.3.3 kept the runtime files of the release before it.
- **One test was corrected** (`tests/desktop-smoke.cjs`). Before it presses Ctrl+W in one of several windows, it now waits until every window is on the screen and the window it means has kept the focus. The reason is under “Tests” and “Found while testing” below. The program was not changed for it.
- Version 1.3.4 in `package.json`, the documents, the text of the web page, and the executable's properties; the line for Electron in `THIRD-PARTY-NOTICES.txt` (its license text is unchanged).

**What the update takes care of, and what it does not.** `npm audit` listed 19 advisories for 1.3.3 and lists 18 now (11 rated high, 3 moderate, 4 low): the one for Electron is gone. Of the others, three are in the program (TipTap, ProseMirror's handling of pasted HTML, KaTeX) and the rest in tools that only build it; none of them was touched, because updating the editing libraries changes how editing behaves and is a decision of its own. The Electron 44 line is scheduled to get fixes until about March 2, 2027 (a tentative date on Electron's schedule); after that, staying current means the next generation of the engine, which is a bigger step than this one.

**Build.** `npm ci` and `npm run build` (TypeScript, Vite) with Node 22.23.5 / npm 10.9.9. The stylesheet (`index-CyLybaO3.css`), the JavaScript bundle (`index-DJg4t7ss.js`) and `index.html` are those of 1.3.3. Rebuilding this source package reproduces `dist/` byte for byte, with the `dist/` folder that comes with the source in place (see the README).

**Tests** (Linux, Electron 44.11.5 official linux-x64 build, Xvfb, US English dictionary):

- `npm test`: 81 passed (37 + 44).
- In the real app: `tests/paragraph-smoke.cjs` (10 checks), `tests/find-smoke.cjs` (13), `tests/undo-smoke.cjs` (5), `tests/pictures-smoke.cjs` (6), `tests/ignore-smoke.cjs` (12), `tests/dictionary-smoke.cjs` (5), `tests/spelling-smoke.cjs` (7), `tests/desktop-smoke.cjs` (19), `settings-smoke.cjs`, `word-count-smoke.cjs`, `typography-smoke.cjs`, `startup-smoke.cjs`, `close-restore-smoke.cjs`, `close-command-smoke.cjs`, `npm run test:equivalence`, `tests/theme-browser-smoke.py` and `tests/colors-browser-smoke.py`: all passed. They are the tests of 1.3.3, except for the wait added to the desktop check (next point). The tests of the spelling features are the ones that depend most on the engine's inner workings (when Chromium rechecks, how it keeps its marks, where it puts the caret at the end of a document); they passed without a change.
- **The desktop check failed once, and the fault was in the check.** In the first run on the files from the Windows ZIP, its step “close a window with Ctrl+W and answer Cancel” failed: a different window had closed. It passed the next 19 runs, so the machine was kept busy to bring the fault out (three processes that do nothing but use its two processors). The check then failed in 2 of 6 runs on the new engine and in 2 of 6 on the old one, at the same two steps, and each time the window created last had closed in place of the one the key was sent to. The check sent its key straight after asking for the focus, and the key was faster than the focus (“Found while testing” below). With the wait in place it passed 8 of 8 runs on the busy machine with the new engine, 8 of 8 with the old one, and 6 of 6 on a quiet machine.
- The paragraph, Find and Ignore All tests were each run several times in a row on the new engine without a failure.
- The safeguards of 1.3.3 were taken out in turn again, on the new engine, and each test failed where it had failed on the old one (thirteen cases, and the empty filler a second time with the test's counts of its length left out): the tests still tell a working safeguard from a missing one.
- The packaged `resources/app` from the Windows ZIP passed the paragraph, Find, Undo, pictures, Ignore All, dictionary, spelling, settings and desktop checks (the desktop check as corrected).

**Compared with 1.3.3 on the old engine** (same machine; for the speed figures the two versions were run in turn):

- *Speed, in the 2 MB document* (248,000 words; four runs each unless said otherwise): typing 32–37 ms per key (31–36 ms on the old engine); with Find open 30–35 ms (36 ms); Find shows its 404 matches 145–183 ms after the last key (159–188 ms); Next 16–18 ms (17–20 ms); closing Find 175–323 ms (179–264 ms; this one varies most from run to run on both); a new paragraph 98–126 ms (102–120 ms; two runs of eight); a blinking recheck brings the red line at the far end back after 2.7–3.5 seconds (2.9–3.4 seconds; twelve measurements each); the quiet check after 2.9–3.7 seconds (3.1–3.4 seconds when 1.3.3 was tested). None of the differences is larger than the difference between two runs of the same version.
- *The quiet check in the long test paragraph* brings the lost red line back after 1.38–1.44 seconds (1.39–1.45 on the old engine; eight tries each).
- *A recheck cut short by a visit to the Find box* was made up for when the caret came back in 30 of 30 tries (85 of 86 on the old engine).
- *The same data folder with both versions.* 1.3.3 on the old engine, then 1.3.4 on the new one, then each once more, all on one data folder: every start restored the document of the run before, a word added to the custom dictionary by one version was known to the other, the program's own files (`session.json`) stayed readable, and neither engine complained about the other's files. **Limitations.**

- **Not run on Windows, and this time that matters more.** Through 1.3.3 the runtime files were those of earlier releases, which had been in use on Windows; only the program's own files were new. Now every file of the runtime is new. What stands behind it: it is Electron's own published build, unchanged; the Linux build of the same release runs every test; and the executable differs from Electron's only in icon, name and version. What is missing is a run on Windows itself. Keep the 1.3.3 folder until 1.3.4 has been used for a while; both work on the same settings and drafts.
- The limitations of 1.3.3 stand unchanged: the rechecks that blink (after a paste, Replace, Ignore All, Clear Custom Dictionary and a return from the source view); the red lines that stay away while the caret is in the Find box if it was opened within a second of such a recheck; the second and a half before a red line returns after Bold, Italic or Enter in a long paragraph; Find's list of at most 500 matches; pictures on a second computer's share not shown, and pictures on the web fetched as before. The picture change of 1.3.3 is about what Windows does when a file on another computer is asked for, which cannot be watched on Linux.

**Found while testing, the same in earlier versions, and not changed.**

- *A key pressed in the instant a large document appears can be undone by the program.* After a document is loaded, the program restores the writing position in two steps, one screen frame apart, and each sets the scroll position. With the 2 MB document that frame lasts about a fifth of a second. Ctrl+End pressed in between puts the caret at the end, and the second step puts the window back at the top; pressed within about a hundredth of a second after it, the window moves and the caret stays. In these tests a key sent the moment the document was shown hit that gap about one time in ten, on either engine, mostly in the first window after the program starts. A scroll made between the two steps is undone in 1.3.2 in the same way. Pressing the key again does what was meant.
- *A menu shortcut acts on the window that has the focus when its command runs.* The windows share one menu, and the command of a shortcut (Ctrl+W, Ctrl+S, Ctrl+F and the rest) runs a moment after the key press, for the window that has the focus then. With a keyboard that is the window the key was pressed in, unless the focus moves in that moment, as it does when a new window appears. A test sends its key by program, and there the order matters. With two windows open and the focus on the second, on either engine: Ctrl+W sent to the first window without asking for the focus did nothing; sent straight after asking for the focus, it closed the second window (5 of 5 tries); sent once the first window had the focus, it closed the first. The desktop check sent its key straight after asking, which worked as long as the window it meant had the focus already, and failed when a window created a moment earlier had just taken it. A window with unsaved changes asks before it closes, whichever window the command reaches, so no writing is lost this way. The 1.3.3 program does the same, and it was left as it is; the check now waits.
- *The formatted view writes Markdown its own way.* A file is rewritten as a whole when it is saved after an edit in the formatted view (the Markdown source view saves exactly what is in it). 72 small files from other sources were opened, edited without changing anything, and saved. Text, headings, emphasis, quotations, links, images, lists, front matter and math came back with the same meaning, in PicoMarQ's notation: `*` for italics, `-` for list items, `#` headings, `---` rules, backtick fences, inline links for reference-style links, Unix line endings, no byte order mark, single blank lines, and no line break at the end of the file. These changed in meaning:
  - Footnotes and citations in Pandoc's notation get backslashes: `[^1]` is saved as `\[^1\]`, `[@smith2020]` as `\[@smith2020\]`, `^[note]` as `^\[note\]`. PicoMarQ shows them as plain text either way, but other programs no longer read them as footnotes or citations. A command such as `\newpage` on a line of its own is saved as `\\newpage`, and a subscript `H~2~O` as `H~~2~~O` (struck through).
  - A code block fenced with tildes (`~~~`) is not shown and is gone from the saved file. Code blocks fenced with backticks or indented are kept.
  - HTML is dropped: a comment disappears, and tags such as `<sub>`, `<span>`, `<kbd>` or `<div>` are removed while the text inside them stays. `<u>` and `<br>` are understood. The entity `&nbsp;` becomes an ordinary space; other entities (`&amp;`, `&mdash;`) are shown and saved as written. A non-breaking space character is kept.
  - In tables, the alignment of columns (`:---:`, `---:`) is lost. A link around an image is lost. Two paragraphs in one list item become one, and blank lines between list items go.
  - A file that ends with a list, a table, an image, a math block or a quotation gets an empty last line with one space in it.
